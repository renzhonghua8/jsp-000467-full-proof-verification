# Kernel rechecking plan for the full Erdős 577 proof

## Supported versions and actual checker flags

The installed Lean 4.33.0 and 4.34.0 sources were inspected directly:

- `src/lean/LeanChecker.lean`
- `src/lean/Lean/Replay.lean`
- `src/lean/Lean/Environment.lean`
- `src/lean/Lean/Util/CollectAxioms.lean`
- `src/lean/Lean/Util/FoldConsts.lean`

Both versions support `--fresh` and `-v` / `--verbose`. Neither implements
`-r` or `--help`. Unknown flags are silently discarded. In particular,
`leanchecker --help` starts an actual default-target check; it is not a
help command. Never use it as feature discovery.

Ordinary `leanchecker ErdosProblems.Erdos577` checks existing modules with
that name prefix. For each module it loads its imports and replays only
the module's own declarations into that imported environment. The imports
are trusted in that individual invocation. A prefix check consequently
does not itself establish that Mathlib's imported declarations were replayed.

`leanchecker --fresh --verbose Jsp467FullReview.Bridge` accepts exactly one
module, loads its full transitive imports including private data, then
replays all loaded constants into an empty environment. It covers the full
proof, the independent statement bridge, and their Mathlib / Lean imports.
One fresh invocation suffices; separately replaying 850 proof modules is
unnecessary and substantially duplicates work.

Lean 4.34 refactored `Environment.replay` to
`Kernel.Environment.replay`; 4.33's checker uses the former and 4.34's the
latter. Their CLI and fresh-environment semantics are the same. Always use
the same toolchain that generated the `.olean` artifacts. This script
refuses a mismatch against the project's pinned version.

## Required prerequisites

Build the proof and `Jsp467FullReview.Bridge` successfully first, using the
project's Lean 4.33.0 and locked Mathlib revision. The audit script only
reads existing compiled artifacts and does not rebuild proof modules.
All `.olean`, `.olean.server`, and `.olean.private` files needed by the
module-system imports must remain available.

Example invocation (from this project directory, with Elan available):

```sh
bash scripts/kernel_audit.sh . "$(lean --print-prefix)/bin" verification/kernel
```

The default target is `Jsp467FullReview.Bridge`. It inspects these theorem
closures independently:

- `Erdos577.erdos_577`
- `Jsp467FullReview.erdos_faudree_full`
- `Jsp467FullReview.erdos_faudree_full_pointwise`

The report is successful only if fresh replay exits successfully and all
three theorem closures contain no axiom outside `propext`,
`Classical.choice`, `Quot.sound`. The JSON lines list the actual axioms,
the visited declaration count, and whether all three standard axioms occur.
A strict subset is logically acceptable and is reported rather than hidden.
Any missing declaration, unsafe/partial dependency, or extra axiom fails.
In particular, `sorryAx` and `Lean.ofReduceBool` are not allowed.

## Axiom inspection and trust boundary

In both installed versions, ordinary `#print axioms` may reuse exported
axiom summaries for imported declarations. `AxiomClosure.lean` instead
loads the module with `withImportModules` (extensions disabled and full
private data loaded) and traverses actual checked constant types and
bodies. Thus it does not trust imported axiom-summary metadata. It is a
read-only verifier program; its `unsafe main` is required by the import
API's memory-lifetime contract and is not part of any mathematical proof.

Fresh replay sends safe total definitions, theorems, axioms, opaque
declarations, and inductive declarations to Lean's kernel. Constructors
and recursors are checked against the versions regenerated by the kernel.
The checker deliberately skips unsafe and partial implementation constants;
these cannot be mathematical dependencies of a well-formed safe theorem,
and the direct axiom inspector additionally rejects them if reachable.
Kernel acceptance does not itself prohibit added axioms, which is why the
separate transitive axiom allowlist check is essential.

Mathlib cache files are used as stored proof terms, not accepted as opaque
certificates of validity: fresh replay rechecks their loaded mathematical
declarations. Source/artifact correspondence is a separate property. A
successful fresh replay says the stored terms are valid; it does not prove
that a downloaded artifact was produced from the claimed source commit.
Pin the manifest, record hashes, and freshly compile the project proof
modules and independent bridge. The remaining trusted computing base is
the selected Lean binary/kernel, its serialization/import implementation,
the verifier code and platform, and the three admitted standard axioms.
This is an independent replay in the same Lean kernel, not a separately
implemented proof checker such as Lean4Lean.

## CI integration

The pinned workflow runs this script explicitly after the normal source and
bridge build, using `--fresh --verbose Jsp467FullReview.Bridge`.
Do not describe a plain namespace-prefix checker run as checking all
Mathlib dependencies. A full fresh check may be expensive because the
upstream proof imports `Mathlib`; give it adequate time and memory and
preserve logs.

Run 35203111492 reached this check after a successful complete source build,
but the job's four-hour limit terminated replay after about 51 minutes.
This is incomplete replay, not kernel acceptance or a reported mathematical
rejection. Replacement run 35226375007 used a six-hour job budget and a
160-minute audit-step limit, with direct axiom-body traversal first and
line-buffered checker output where `stdbuf` was available. It completed the
unchanged full `--fresh` scope successfully. The combined audit command took
2:01:54, reached 8,764,992 KiB maximum resident memory, and exited with status
0. The three direct theorem-body reports each contained exactly `propext`,
`Classical.choice`, and `Quot.sound`, with no disallowed axiom.
